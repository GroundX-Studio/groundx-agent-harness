# Product: Master-Brand Framing

This file translates current product state into Valantor-altitude framing. It
does not own lifecycle state, promise boundaries, verification events, or
recheck triggers. The single installed owner for those facts is
`../../product-brand-gtm/references/product.md`.

## Required workflow

1. Read `../../product-brand-gtm/references/product.md`.
2. Select the current record for every product named in the output.
3. Carry its state and promise boundary into the answer without strengthening
   either.
4. Apply the stable master-brand framing below.
5. Retrieve claim payloads from
   `../../product-brand-gtm/references/proof-points.md`; use
   `proof-points.md` only to choose a master-brand angle.

If collateral conflicts with the canonical product-state owner, use the
canonical record and request a reviewable approved update to that record. Do not
invent an owner or confirmation event, and do not create a second lifecycle
record here.

## Hosted GroundX

At master-brand altitude, position the hosted distribution as an accessible
evaluation and integration path into Valantor's Visual Intelligence platform.
Do not include signup, conversion, dashboard, or implementation commentary.
Use the canonical product-state owner before making any availability claim.

## GroundX On-Prem

Position the self-hosted distribution as the path for running Visual
Intelligence inside a customer-controlled perimeter. Regulated industries and
data-sovereignty buyers may treat that deployment posture as a prerequisite.
Retrieve deployment detail from `groundx-on-prem` and any current third-party
validation from the canonical proof owner.

## GroundX Studio

Position the UI as the business-user surface for seeing and using Visual
Intelligence without beginning from a custom API integration. Preserve the
intended use-case names **Extract**, **Interact**, and **Report** when the
canonical product-state owner permits them. Do not include prototype or rebuild
history.

## GroundX Harnesses

The adoption layer contains two distinct GroundX bundles:

- **GroundX Agent Harness** is the public GroundX knowledge and workflow
  bundle.
- **GroundX On-Prem workspace service** is customer-deployable and covered by
  public operator guidance.
- **GroundX Studio Harness** is the private expanded bundle with prebuilt Studio
  production, authoring, publishing, administration, and operational workflows
  that may use the workspace service.

At master-brand altitude, the Harness story is implementation leverage:
compatible agents receive GroundX-specific knowledge and workflows for
GroundX-backed work. GroundX MCP remains optional connected execution, and the
host agent may supply separate creation capabilities. Use
`../../product-brand-gtm/references/harness-pitch.md` for capability
attribution, and read the canonical product-state owner before claiming
availability.

## Outcome Plug-ins

Position an Outcome Plug-in as a repeatable vertical product built on GroundX,
not as bespoke consulting or a generic feature bundle. Use the canonical
product-state owner to determine which named plug-ins may be described as
available, illustrative, or otherwise lifecycle-constrained.

For an eligible insurance-fraud product, the master-brand angle is a
productized investigation outcome with source-linked evidence and reviewable
work. For an eligible document-operations product, the angle is modernization
of brittle OCR-and-human-review workflows. Use `outcome-playbooks.md` for the
vertical story, but never let that narrative override the canonical state.

## Operational Layer

The stable strategic framing is outcomes-as-a-service: customers buy a governed
business outcome rather than assembling and operating the underlying
toolchain. AI plus human accountability is central to that framing. Any claim
that this is currently available, deployed, staffed, or sold requires an
affirmative promise boundary in the canonical product-state owner.

## How to use this file

- For “what exists now?” or “what can we promise?”, answer from
  `../../product-brand-gtm/references/product.md`.
- For “how does this fit the Valantor story?”, apply the corresponding section
  here after reading the state owner.
- For customer, benchmark, partner, adoption, or performance evidence, retrieve
  the claim from `../../product-brand-gtm/references/proof-points.md`, then use
  `proof-points.md` to select the master-brand framing.
- For mechanism, defer to
  `../../product-brand-gtm/references/technical-architecture.md`.
- For visual decisions, defer to the master-brand design standards.

This file does not own pricing, terms, customer outcomes, lifecycle state,
technical behavior, or visual design.
